# Architectural Review: `bws git-workflow`

## 1. Critical Analysis & Flaws

### 1.1 The `.git` Sandbox Escape (Critical Security Risk)
**Flaw:** The most dangerous aspect of using `git worktree` for an untrusted AI agent is the shared `.git` directory structure. In a git worktree, the `.git` file points back to the host repository's `.git/worktrees/<name>` directory. This shares the object database, config, and crucially, **git hooks** with the host repository.
**Exploit:** An autonomous agent running with full write access could write a malicious executable script to `.git/hooks/pre-commit` (or alter the git config to run an arbitrary binary via core.pager, etc.). When the developer on the host later runs `git commit`, the malicious script will execute **on the host, completely outside the sandbox**, with the developer's full privileges.
**Resolution:** Never expose the host's `.git` directory (even via worktree linkage) to an untrusted sandbox if the sandbox requires write access. Instead of `git worktree`, use an **ephemeral local clone** (`git clone file://$(pwd) /path/to/ephemeral`). This gives the agent a fully functional but completely isolated `.git` directory.

### 1.2 State & Dependency Paralysis
**Flaw:** A fresh `git worktree` or clone will not contain ignored files such as `node_modules`, `target/`, `.venv`, or local configuration like `.bws/config.jsonc`. If the AI agent attempts to run a build or execute tests to verify its code, it will fail unless it re-downloads and re-compiles everything. If network access is restricted (`--no-network`), the agent is completely paralyzed.
**Resolution:** `bws` needs a mechanism to inject or overlay these directories. Since `bwrap` doesn't natively do writable OverlayFS without root, you can:
1. Bind-mount them read-only (agent can't install new packages, but can run existing ones).
2. Use a CoW (Copy-on-Write) filesystem feature like `btrfs`/`reflink` copies if supported (e.g., `cp --reflink=auto`).
A practical approach is to bind-mount them read-only by default, or provide a flag `--sync-deps=node_modules,.venv` which performs a fast `cp -a --reflink=auto`.

### 1.3 The Auto-Commit Assumption
**Flaw:** Automatically committing all changes (`git add -A`) post-exit might include garbage files generated by the agent (e.g., debug logs, `.pyc` files, test artifacts).
**Resolution:** Allow the interactive triage prompt to handle the commit, or stash the changes into a temporary commit that the user can interactively review and optionally reset (`git reset --soft HEAD~1`).

## 2. Git Plumbing & Edge Cases

### 2.1 Location of the Sandbox
- Putting the worktree in `.git/bws-worktrees/` hides it from standard tools, but if we adopt the "ephemeral clone" approach for security, placing it in `/tmp/bws-agent-workspace-XXXXXX` (or an ephemeral `tmpfs`) is vastly superior. It ensures the environment is automatically wiped on a reboot and doesn't bloat the host `.git` dir if `bws` crashes.

### 2.2 Detached HEAD and Dirty States
- **Dirty Host:** If the host working tree has uncommitted changes, `bws` should either refuse to run (`bws` should not implicitly mangle the user's working state) or require an explicit `--stash` flag which automates `git stash -> clone -> stash pop` in the sandbox.
- **Merge Conflicts on Triage:** If the developer modifies the host base branch while the agent is running in the background, merging the agent's work will result in a conflict. The interactive prompt must detect conflicts (using `git merge-tree`) and offer a `[c] Resolve Conflicts` option, which could drop the user into their `$EDITOR` or a sub-shell.

### 2.3 Unexpected Termination & Orphaned State
- If the `bws` launcher is killed with `SIGKILL`, the ephemeral clone or worktree is left behind.
- **Mitigation:** Implement robust signal handling in Go (`os/signal.Notify`) to clean up on `SIGINT`/`SIGTERM`.
- **GC Command:** Implement a `bws gw clean` command to find and remove old, abandoned worktrees or temporary clones.

## 3. Concrete Improvements & Best Practices

### 3.1 The "Clone-Fetch" Pattern (Recommended Architecture)
To eliminate the git hooks escape vulnerability while maintaining full functionality, implement this workflow:
1. **Init:** `git clone --branch bws-agent-task file://$(pwd) /tmp/agent-env-XXXX`
2. **Setup:** Mount `/tmp/agent-env-XXXX` as the RW workspace in `bwrap`. Link or copy `.bws/config.jsonc` and `.env`.
3. **Execute:** Run the AI agent. The agent interacts with an isolated `.git` directory.
4. **Post-Exit:** On the host, `bws` fetches the branch back:
   `git fetch /tmp/agent-env-XXXX bws-agent-task:bws-agent-task`
5. **Triage:** Display the diff (`git diff HEAD..bws-agent-task`). Let user Merge, Squash, Keep, or Discard.
6. **Cleanup:** `rm -rf /tmp/agent-env-XXXX`

### 3.2 Triage CLI UX Design
The interactive prompt should be clear, showing a summary of the impact and offering decisive actions.

```text
Agent session ended. 3 files modified, 1 new file.

  src/main.go       | 15 +++++++---
  src/config.go     |  2 +
  internal/tests.go | 45 ++++++++++++++++++++++++++++++
  3 files changed, 55 insertions(+), 3 deletions(-)

What would you like to do with agent branch 'bws-agent-task'?
  [m] Merge   - Fast-forward or merge into current branch
  [s] Squash  - Squash into a single commit on current branch
  [k] Keep    - Keep branch 'bws-agent-task' for manual review
  [d] Discard - Delete branch and discard all changes
  [v] View    - Open 'git diff' in pager
> _
```
